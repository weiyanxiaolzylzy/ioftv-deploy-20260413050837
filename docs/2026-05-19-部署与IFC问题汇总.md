## 2. 发现过的原始报错

### 2.1 Docker 权限错误

服务器执行：

```bash
docker compose up -d --build
```

报错：

```text
permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

结论：

- 这是服务器用户权限问题，不是项目代码问题
- 需要使用 `sudo docker compose ...`，或把当前用户加入 `docker` 组

---

### 2.2 IFC 查看器 404

浏览器曾报错：

```text

```

结论：

- 服务器最初缺少 `ifc/dist`
- 后端虽然有 `/ifc` 静态托管逻辑，但目录不存在时不会挂载

已验证：

```bash
curl -I http://127.0.0.1:8890/ifc/
```

后续返回：

```text
HTTP/1.1 200 OK
```

说明：

- IFC 查看器静态资源问题已修复

## 4. 关键根因总结

### 4.1 `/ifc` 查看器最初打不开的根因

根因：

- 服务器部署目录或镜像中最初缺少 `ifc/dist`

影响：

- `/ifc` 路由 404
- iframe 查看器无法拉起

当前状态：

- 已修复

---

### 4.2 老项目 IFC 加载失败的根因

项目：

- `p1779054129761`
- `国际智能制造输配电设备`

根因：

- 数据库里 `ifc_url` 指向 `/uploads/ifc/1779054125326__________________________________.ifc`
- 该文件在服务器上已经不存在

影响：

- 该项目 IFC 文件无法加载
- 即使查看器本身可用，该项目仍会失败

处理建议：

1. 最稳妥：重新上传该项目 IFC
2. 或者把数据库 `ifc_url` 改到一个确认正确存在的新文件

---

### 4.3 “上传 IFC 后提示未解析到构件”的根因

根因：

- 前端原先只用 `parse.elements` 计算“识别到的构件数量”
- 后端导入项目时实际优先使用 `assemblySummaries / IFCELEMENTASSEMBLY`
- 某些 IFC 文件里可导入对象主要体现在装配体汇总，不在前端原先的统计口径里

表现：

- 上传成功
- 解析成功
- 但前端仍提示“未解析到构件”或识别数为 `0`

当前状态：

- 已修改前端口径，与后端统一

## 6. 重新部署前注意事项

### 6.1 必须确认 IFC 查看器构建产物存在

服务器部署前或镜像构建前，必须确认：

```bash
ifc/dist/index.html
```

如果没有，需要先执行：

```bash
cd /opt/ioftv/ifc
npm install
npm run build
```

---

### 6.2 Docker 重新部署时的注意事项

如果当前用户没有 Docker 权限，需要：

```bash
sudo docker compose up -d --build
```

---

### 6.3 部署后必须检查的接口

建议部署后按顺序验证：

```bash
docker compose ps
curl http://127.0.0.1:8890/health
curl -I http://127.0.0.1:8890/ifc/
curl -I http://127.0.0.1:8890/uploads/ifc/具体文件名.ifc
```

判定标准：

1. `/health` 必须 `200`
2. `/ifc/` 必须 `200`
3. 新项目 IFC 文件地址必须 `200`

---

### 6.4 对旧项目数据的注意事项

不是所有项目的 `ifc_url` 都一定对应当前服务器上真实存在的文件。

例如今天已确认：

- `p1779054129761` 对应 IFC 文件不存在

所以重新部署后，如果某个旧项目查看器仍失败，优先检查：

```bash
curl -I http://127.0.0.1:8890/uploads/ifc/该项目数据库里的文件名.ifc
```

不要先怀疑查看器本身。
